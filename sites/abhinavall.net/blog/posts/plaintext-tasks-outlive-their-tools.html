Plain-Text Tasks Outlive Their Tools

A developer on YouTube recently walked through Tuxedo, a terminal task manager he found on GitHub. The tool is pleasant. More interesting is what he quietly chose to build on: a plain-text format called todo.txt that predates most of its competitors. His interface is new and disposable. The underlying file format is old and durable. That ordering is the lesson.

The format is the product

In the video, the author explains that he moved his tasks off an Obsidian vault because they kept getting lost and pulling him into context switches. What he wanted was every task aggregated per project. Tuxedo gives him that view, and underneath it writes an ordinary todo.txt file: one line per task, a priority in parentheses, +project and @context tags, all of it readable by a person or a script.

The TUI is the pleasant part, but the durable part is that file. You can grep it, diff it in git, sync it across machines, and open it in Vim, a Neovim plugin, or the small phone web form the demo shows. Swap the interface and the data survives. This is the Unix instinct applied to personal task tracking: keep state in a dumb, legible format, then let many small tools read and write it.

Where the line-based bet strains

Honesty about the format means looking at what the demo quietly piles onto a single line. Due dates, weekly recurrence, priority cycling, and a phone capture server that reads a sentence like "pay rent, show three days before" and files it correctly. Those live as key:value pairs and conventions stacked on top of the original spec.

Each feature that needs real structure nudges a line-based file toward an implicit schema only one tool fully understands. Recurrence is the clearest case: the file can store the rule, but something has to interpret it, and that something is Tuxedo. Priorities past D lose their special color, metadata starts to accumulate, and two machines editing the same file will eventually hit a merge conflict the demo never has to face. Emacs org-mode walked into this wall years ago. A format can stay human-readable while slowly becoming tool-specific.

Why a grep-able task file matters more in 2026

Here is the part the video does not reach for, and the reason the durability argument is stronger now than it was a few years ago. Coding agents have started reading and writing project state directly. A task list that lives as a plain file inside the repository is something both a developer and an agent can open, edit, and diff. The same list trapped in a proprietary app's database stays out of reach without an integration nobody wants to maintain.

A todo.txt file is an interface humans and machines share without an API in between. An agent can append a task, tick one off, or check what is blocked using the exact file the developer edits in Neovim. Per-project scoping, the author's original motivation, is also how an agent should narrow its attention. That same legibility, diffable and free of lock-in, is what lets the format outlast interface churn while doubling as shared memory for human and agent workflows.

Takeaway

If you are choosing a task system, separate the durable data from the disposable interface, and prefer a format that you and a machine can both read without anyone's permission. Tuxedo is a well-built front door. The todo.txt file behind it is the house worth keeping. It was young when the video was recorded, on the order of a hundred GitHub stars, so treat it as a promising early tool rather than a settled dependency.
